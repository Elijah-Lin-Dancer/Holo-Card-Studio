# 系统设计 · HoloLab Studio

> 目标：一条可复现的 AIGC 全链路 —— 一句话/一张照片 → 四层素材 → Blender 3D
> 场景 → Three.js 实时查看器 → 纯静态在线展厅。**零服务器、零数据库**，
> 全链路可离线复现。

## 1. 设计目标与约束

| 约束 | 决策 |
|---|---|
| 公开给所有人用 | 展厅做成纯静态站点，GitHub Pages 免费托管 |
| 不维护服务器/数据库 | 卡片清单用 `cards.json`，资产为静态文件；生成在本地完成 |
| 生成质量可控、可复现 | 四层素材**分而治之**，每层用最合适的工具 |
| 作品集可展示工程能力 | 流水线、发布脚本、CI、文档全自动化、可审计 |

## 2. 分层架构

```
┌───────────────────────────────────────────────────────────┐
│ 展示层（gallery/）                                         │
│  瀑布流首页（cards.json 驱动） → 卡片页（Three.js 查看器）    │
│ 纯前端 · 无后端 · 可离线部署                                 │
├───────────────────────────────────────────────────────────┤
│ 发布层（publish_card.py）                                  │
│ 校验产物 → 生成缩略图 → 归档 + 共享 vendor → 更新清单        │
├───────────────────────────────────────────────────────────┤
│ 生成层（run_pipeline.py）                                  │
│ 素材校验 → Blender 构建/渲染/导出 → 网页模板组装 → npm 依赖  │
├───────────────────────────────────────────────────────────┤
│ 素材层（ai_generate.py）                                   │
│ 豆包 Seedream 分层生成 → rembg 抠图 → OpenCV 线稿 → 字体排版 │
└───────────────────────────────────────────────────────────┘
```

各层之间通过**磁盘上的标准产物**解耦（`assets/*.png`、`card.blend`、`web/`），
任意一层可独立替换或调试。

## 3. 关键设计决策

### 3.1 为什么素材分四层，而不是一张整图？

一张整图只能做到"平面"：视差需要主体与背景**分离移动**，镭射/线稿/文字也需要
独立控制。四层结构与原项目 Blender 材质节点一一对应：

| 层 | 作用 | 生成方式 |
|---|---|---|
| `subject.png` | 前景主体，透明底，随视角前凸 | Seedream 生成 → rembg 抠图 |
| `background.png` | 背景环境，随视角后缩 | Seedream 独立生成（同风格空镜） |
| `lineart.png` | 白底黑线，发光描边 | OpenCV 从透明主体提取（**保证像素级注册**） |
| `text.png` | 卡面文字 | 字体渲染（**不让 AI 画字**，保证字形正确） |

### 3.2 为什么线稿用程序化提取而不是让 AI 重画？

AI 重画线稿无法保证与主体的**位置、比例、轮廓一致**（registration），而线稿要叠
在主体轮廓上发光。用 OpenCV 从抠图后的透明主体直接提取轮廓 + 内部 Canny 边缘，
天然对齐。这是与原项目（靠 Codex 人工 trace）的差异点之一。

### 3.3 为什么展厅用共享 vendor 而不是每卡自带依赖？

每张卡若自带 node_modules（约 4MB three 包），展厅体积随卡数线性膨胀。改为
`gallery/vendor/three/` 共享依赖，发布脚本把每卡 index.html 的 importmap 改写为
相对路径指向共享目录。归档体积从每卡 ~47MB 降到 ~14MB（且后续可继续压缩素材）。

### 3.4 为什么 Blender 用便携版自动下载？

Blender 体积大（~1.2GB 解压）、系统依赖复杂，让用户手动安装门槛高。流水线
`ensure_blender.py` 自动下载官方包并做 SHA-256 校验；国内网络可预先把包放入
`tools/`（从清华镜像下载同名文件），流水线检测到即复用。

### 3.5 构图一致性如何缓解？

主体图与背景图是两次独立生成，构图不可能像素级一致。缓解手段：

1. 提示词共享同一**风格前缀**，且背景描述显式"中下部留白、不出现主体"；
2. 背景在主体区域刻意"安静"，主体是前景遮挡层，视差移动时轻微错位不违和；
3. 代码与文档如实记录该 tradeoff（作品集里诚实 > 完美）。

## 4. 数据流（一次完整发布）

```
card-config.json ──► ai_generate.py ──► assets/{subject,background,lineart,text}.png
                                              │
run_pipeline.py ◄──────────────────────────────┘
  ├─ validate_assets.py（alpha / 线稿极值 / 尺寸校验）
  ├─ ensure_blender.py（便携版 + SHA-256）
  ├─ build_card.py（Cycles 渲染 renders/hero.png + card.blend）
  ├─ export_web.py（GLB + 材质槽替换）
  └─ web 模板组装 + npm install
                                              │
publish_card.py ◄──────────────────────────────┘
  ├─ 缩略图 thumb.jpg（420px）
  ├─ 归档 gallery/cards/<id>/（剔除依赖）
  ├─ importmap → 共享 vendor
  └─ cards.json 更新（去重 + 新卡置顶）
                                              │
git push ──► GitHub Pages ──► https://<user>.github.io/<repo>/
```

## 5. 可审计性

- 每张卡保留 `work/` 中间产物（AI 原图、抠图结果）与 `verification.json`
  （Blender 版本、设备、材质、参数）；
- 发布脚本幂等：重复发布同一张卡会先移除旧归档、清单去重；
- 密钥管理：`.env` 被 `.gitignore` 排除，公开仓库不含任何密钥。

## 6. 已知边界与后续

- 网页素材为 1920×2880 原图（~14MB/卡），后续加压缩步骤优化首屏；
- lenticular（双图光栅）模式为原项目第二条路线，尚未接入；
- 展厅自动分类（按人物/风格/稀有度）为后续迭代项。
